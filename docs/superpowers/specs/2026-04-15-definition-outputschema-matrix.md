# Definition Output Schema Matrix

## Goal

This document is the authority for migrating all action and skill definitions to the current StateResolver output model.

It defines:

- which state change types each definition may output
- when to use `presets: [default]`
- which legacy guidance terms must be removed or rewritten
- how witness memories are handled after this migration

This migration uses a **wide but grounded** rule:

- allow state changes that are semantically plausible for the definition
- do not widen schemas with unrelated types just to avoid edge cases
- if a structure has no current standard state change type, do not promise it as structured output

## Standard State Change Types

The only supported structured output types for definition-level `outputSchema` are:

- `character.hp`
- `character.san`
- `character.fatigue`
- `character.condition`
- `character.position`
- `item.move`
- `item.modify`
- `item.destroy`
- `item.create`
- `scene.condition`
- `memory.event`
- `memory.information`
- `relationship.change`

`memory.witness` remains a valid engine memory type, but after this migration it is **runtime-managed only** and should not appear in definition `outputSchema`.

## Preset Rules

Current preset usage:

- `default`
  - `memory.event`
  - `character.fatigue`
  - `scene.condition`
- `item_modify`
  - `item.move`
  - `item.modify`
  - `item.destroy`
  - `item.create`
  - `memory.information`

Usage rules:

- Use `presets: [default]` when the definition normally produces a first-hand event memory and may reasonably cost effort or time.
- Use `item_modify` as the single reusable item-state output family for item-centric skills instead of duplicating the same `use` lists in multiple definitions.
- Do not use `default` for low-effort social exchanges like `conversation` or `item_exchange`.

## Legacy Term Mapping

Replace all legacy structured-output language with current state change types.

| Legacy term | Replace with |
| --- | --- |
| `items` | `item.move`, `item.modify`, `item.destroy` |
| `newItems` | `item.create` |
| `addSceneConditions` / `removeSceneConditions` | `scene.condition` |
| `moveTo` | `character.position` |
| `hpDelta` | `character.hp` |
| `sanDelta` | `character.san` |
| `fatigueDelta` | `character.fatigue` |
| `addItems` / `removeItems` | `item.move` |
| `memory` | `memory.event` or `memory.information`, depending on whether it is experiential or learned |

Do not leave old JSON examples in any guidance body.

## Deferred / Unsupported Structured Concepts

These may still be mentioned in prose guidance, but they must not be promised as structured JSON outputs in this migration:

- `connectionEffects`
- `appearanceChange`
- `learnedLocationNames`
- any bespoke `outcome` / `narrative` / `result` field not declared as `custom`

If a legacy example relies on one of these, remove the JSON example or rewrite the effect into existing state change types plus memory text.

## Witness Policy

Definition migration rule:

- remove `memory.witness` from all definition `outputSchema`

Runtime rule:

- witness memories are generated by a separate runtime observation step
- this step runs on the same impact threshold currently used by `impactPipeline`
- it uses event perspective, time, location, and affected NPC selection
- it writes `witness` memories outside definition state resolution

This means definition guidance should no longer instruct the LLM to emit witness memory arrays.

## Family Rules

### Generic / root definitions

- `action`: can affect actor state, scene state, item state, and learned information from searching or examining
- `movement`: only movement, fatigue, and actor event memory
- `conversation`: no fatigue by default; social memory, learned information, relationship shifts
- `character_interaction`: wide umbrella; can affect bodies, positions, items, fear/sanity, and relationship
- `item_exchange`: narrow; transfer item plus memory and relationship
- root-level item manipulation is handled by `action`; the dedicated item root definitions are removed and replaced by the shared `item_modify` preset reused by relevant skills

### Social / investigation

- `perception`, `listen`, `track`: usually event + information, sometimes scene/item state
- `charm`, `bluff`, `persuade`: social memory, information, relationship, possible condition
- `intimidate`: same as above, with possible `character.san`
- `psychology`: mostly event + information

### Knowledge / language / research

- default pattern is `default + memory.information`
- `forbidden_lore` additionally allows `character.san`

### Medical / repair / technical / navigation / survival

- healing: character state + `default`
- repair: item state + `default`
- `locksmith`: item state + `scene.condition` + `default`
- `forgery`: item creation/modification + `default`
- navigation and survival: `default + memory.information`, with survival also allowing concrete physical harm/conditions

### Physical / stealth / combat

- locomotion skills may include `character.position`
- stealth/disguise/sleight-of-hand focus on concealment, condition, or item movement
- combat and weapons use actor event memory plus direct physical consequences on targets

## Runtime Witness Migration Rules

- `runImpactGateForNpc` should stop producing `witnessEntry`
- add a separate observation/witness synthesis step that:
  - runs on current impact thresholds
  - takes affected NPC, perspective, triggering events, current time, and reaction memory context
  - returns a short observation string only
- `impactPipeline` should:
  - build observation first
  - write `event` or `witness` memory from that observation
  - then call impact gate for intent/replan decisions using the same triggering event summary
- all feature tests mocking `runImpactGateForNpc` must be updated to the new contract

## Acceptance Criteria

- all definition files use only current state change types
- no definition `outputSchema` contains `memory.witness`
- legacy JSON schema examples are removed or rewritten
- loader and resolver tests pass
- runtime still writes witness memories through the new observation path
