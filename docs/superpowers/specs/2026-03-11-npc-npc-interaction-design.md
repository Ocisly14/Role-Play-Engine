# NPC-NPC Interaction Design

## Problem

The current system has three gaps in NPC-to-NPC interaction:

1. **One-sided memory** — When NPC A interacts with NPC B, only A gets a memory record. B has no recollection of the interaction.
2. **No proactive socializing** — NPCs lack relationship context during planning, so they never autonomously decide to seek out conversations.
3. **No information propagation** — There is no mechanism for NPCs to share information with each other, with personality-driven distortion as information passes between characters.

## Design

### 1. Unified `chat` Node

All NPC-to-NPC information exchange is modeled as a single plan node type: `chat`.

**Core model:** NPC retrieves from memory → LLM generates interaction outcome → new memories written per participant.

#### PlanNode Extension

```typescript
actionType: "chat"

chatPayload: {
  participantIds: string[]  // All NPC IDs in the conversation (including initiator)
  prompt: string            // Direction hint generated by planning LLM (e.g. "ask about last night's noise at the dock")
}
```

A 1-on-1 conversation is just `participantIds.length === 2`. No separate `share_information` or `group_conversation` types needed.

#### Execution Flow (in tickProcessor)

1. Collect for each participant:
   - NPC personality/profile
   - Relevant memories via `MemoryRetriever.query()` using `chatPayload.prompt` as query, profile: `"conversation"`
2. Single LLM call with all participants' personality + memory context + prompt
3. LLM outputs structured result: new memories per participant ID
4. Write memories to `MemoryStore` per NPC
5. Trigger impact propagation for non-participating NPCs in the same scene (witness mechanism)

#### LLM Output Structure

```typescript
{
  memories: {
    [npcId: string]: Array<{
      type: NpcMemoryType       // conversation, clue, emotion, relationship, etc.
      content: string           // Content filtered through this NPC's personality/perspective
      metadata: object          // Type-specific metadata
    }>
  }
}
```

No conversation transcript is generated — only the resulting memories per participant.

#### Participant Conflict Handling

- If a participant NPC is not in the same scene/location, remove them from participantIds
- Execute only if remaining participants >= 2, otherwise cancel the node

#### Cost

One LLM call per chat execution regardless of participant count. Multi-party conversations are cheaper than equivalent pairwise interactions.

### 2. Bilateral Memory (Mirror Write)

For all non-`chat` NPC interactions (combat, stealth, etc.), the passive side now also receives memory.

#### Mirror Write Rules

When NPC A performs a `character_interaction` on NPC B:

- **A side**: Existing logic unchanged (already writes conversation + relationship memory)
- **B side**: New mirror write in tickProcessor post-execution:
  - `conversation` memory: "A [action] me, result was [outcome]" with `withCharacterId` pointing to A
  - `relationship` memory: same `scoreDelta` as A's record

Mirror write is a direct copy with perspective flip — no LLM call needed.

`chat` nodes do NOT use mirror write. They use the LLM-generated per-participant memory output directly.

### 3. Proactive Socializing via Planning

#### Prompt Injection

Inject into `generateDailySchedule()` and `generateDetailedNodes()` prompts:

1. **Relationship summary** — From `npcRelationshipGraph`: each related NPC's name, score, and most recent relationship memory summary
2. **Recent social memories** — Last 5 `conversation` type memories for this NPC

With this context, the planning LLM can naturally generate `chat` nodes (e.g., "go find Sarah to discuss last night's events") or choose not to socialize — driven entirely by personality and memory.

#### Planning Prompt Addition

The planning prompt explains the `chat` action type and its payload format so the LLM can output it when appropriate.

### 4. Information Distortion (Gossip)

No separate distortion step. Distortion happens naturally during `chat` execution:

- The chat LLM prompt instructs the model to filter shared information through each NPC's personality, biases, and emotional state
- NPC A recalls "Tom carried a strange box at midnight" → A is paranoid → B receives memory: "According to A, Tom was secretly smuggling suspicious cargo at the dock, possibly contraband"

#### Source Tracking

Each memory produced by a `chat` node includes in its metadata:

```typescript
metadata: {
  sourceType: "chat"
  chatParticipantIds: string[]  // All participants in this chat
  // ... plus each handler's existing metadata fields
}
```

No complex source chain tracking. Information propagation paths can be reconstructed by correlating memory timestamps and participant overlaps across multiple chat records.
