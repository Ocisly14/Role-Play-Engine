# NPC-NPC Interaction Design

## Problem

The current system has three gaps in NPC-to-NPC interaction:

1. **One-sided memory** — When NPC A interacts with NPC B, only A gets a memory record. B has no recollection of the interaction.
2. **No proactive socializing** — NPCs lack relationship context during planning, so they never autonomously decide to seek out conversations.
3. **No information propagation** — There is no mechanism for NPCs to share information with each other, with personality-driven distortion as information passes between characters.

## Design

### 1. Unified `chat` Node

All NPC-to-NPC information exchange is modeled as a single plan node type: `chat`.

**Core model:** NPC retrieves from memory → LLM generates interaction outcome → new memories written per participant.

#### PlanNode Extension

`chat` is a new `PlanNodeType` (added to `BuiltinNodeType` union), NOT a new `ActionType`. Chat has no skill roll or success/failure mechanic — it is pure information exchange.

```typescript
// In types.ts — BuiltinNodeType
export type BuiltinNodeType =
  | "routine"
  | "movement"
  | "character_interaction"
  | "object_interaction"
  | "scene_interaction"
  | "chat";                      // NEW

// New payload interface
export interface ChatPayload {
  participantIds: string[]       // All NPC IDs in the conversation (including initiator)
  prompt: string                 // Direction hint generated by planning LLM
}

// PlanNode gets optional chatPayload field
export interface PlanNode {
  // ... existing fields ...
  chatPayload?: ChatPayload;
}
```

A 1-on-1 conversation is just `participantIds.length === 2`. No separate types needed.

#### Execution Flow (in tickProcessor)

`chat` nodes bypass the standard `registry.getHandler()` → `CharacterAction` path. Instead, tickProcessor branches on `node.type === "chat"`:

1. Validate: all participantIds are alive, conscious, and in the same scene. Remove absent ones. Cancel if < 2 remain.
2. Collect for each participant:
   - NPC personality/profile
   - Relevant memories via `MemoryRetriever.query()` using `chatPayload.prompt` as query, profile: `"conversation"`
3. Single LLM call with all participants' personality + memory context + prompt
4. LLM outputs structured result: new memories per participant ID
5. Validate LLM output. On malformed response: write a minimal `conversation` memory for each participant ("Had a conversation with [others]") and continue.
6. Write memories to `MemoryStore` per NPC, with `sourceType: "chat"` and `chatParticipantIds` in metadata
7. Create a synthetic `CharacterAction` for the tick log (status: "completed", outcome: summary of chat) so downstream processing (tick result, player witness) still works
8. Trigger impact propagation for non-participating NPCs in the same scene via witness mechanism. The witness event uses the synthetic `CharacterAction` from step 7.

#### LLM Output Structure

```typescript
{
  memories: {
    [npcId: string]: Array<{
      type: NpcMemoryType       // conversation, clue, emotion, relationship
      content: string           // Content filtered through this NPC's personality/perspective
      metadata: object          // Type-specific metadata fields
    }>
  }
}
```

Valid memory types in chat output: `conversation`, `clue`, `emotion`, `relationship`. Other types (`belief`, `plan`, `secret`, etc.) are not produced by chat — beliefs form through the reasoning system, plans through the planning system.

No conversation transcript is generated — only the resulting memories per participant.

#### ConversationMetadata for Multi-Party Chat

The existing `ConversationMetadata.withCharacterId` (singular) stays as-is. For multi-party chats, each participant's `conversation` memory sets `withCharacterId` to the "primary other" (the chat initiator, or most relevant counterpart). The full participant list is available via `chatParticipantIds` in the chat source metadata.

#### Deduplication

If two NPCs both plan `chat` nodes targeting each other in the same tick, deduplicate by sorted participant pair key (same approach as `scanUnplannedEncounters`). The first node executes; the duplicate is skipped.

#### Interaction with `scanUnplannedEncounters`

`scanUnplannedEncounters` currently injects `character_interaction` nodes for co-located NPCs with |relationship score| >= 60. After this feature, it should check whether a `chat` node already exists for the same pair before injecting an encounter.

#### Participant Limit

Practical upper bound: 5 participants per chat. Beyond this, the LLM context becomes unwieldy and output quality degrades. The planning prompt should note this limit.

#### Cost

One LLM call per chat execution regardless of participant count. Multi-party conversations are cheaper than equivalent pairwise interactions.

### 2. Bilateral Memory (Mirror Write)

For NPC-to-NPC `character_interaction` nodes (not `chat`, not player-involved), the passive side now also receives memory.

#### Mirror Write Rules

When NPC A performs a `character_interaction` on NPC B (both are NPCs, not players):

- **A side**: Existing logic unchanged (already writes conversation + relationship memory)
- **B side**: New mirror write in tickProcessor post-execution:
  - `conversation` memory: "A [action] me, result was [outcome]" with `withCharacterId` pointing to A
  - `relationship` memory: same `scoreDelta` as A's record

Mirror write is a direct copy with perspective flip — no LLM call needed.

Player-involved interactions already have their own memory write path (tickProcessor lines 487-513) and are not affected.

`chat` nodes do NOT use mirror write. They use the LLM-generated per-participant memory output directly.

### 3. Proactive Socializing via Planning

#### Prompt Injection

Inject into `generateDailySchedule()` and `generateDetailedNodes()` prompts:

1. **Relationship summary** — From `npcRelationshipGraph`: each related NPC's name, score, and most recent relationship memory summary
2. **Recent social memories** — Last 5 `conversation` type memories for this NPC

With this context, the planning LLM can naturally generate `chat` nodes (e.g., "go find Sarah to discuss last night's events") or choose not to socialize — driven entirely by personality and memory.

#### Planning Prompt Addition

The planning prompt documents the `chat` node type and `ChatPayload` format. Example instruction for the LLM:

```
When this NPC wants to have a conversation or share information with other NPCs,
use node type "chat" with a chatPayload:
- participantIds: list of NPC IDs involved (including this NPC)
- prompt: a brief description of what this NPC wants to discuss

The chat system will handle the actual conversation based on each
participant's personality and memories. Max 5 participants per chat.
```

### 4. Information Distortion (Gossip)

No separate distortion step. Distortion happens naturally during `chat` execution:

- The chat LLM prompt instructs the model to filter shared information through each NPC's personality, biases, and emotional state
- NPC A recalls "Tom carried a strange box at midnight" → A is paranoid → B receives memory: "According to A, Tom was secretly smuggling suspicious cargo at the dock, possibly contraband"

#### Source Tracking

Each memory produced by a `chat` node includes in its metadata:

```typescript
metadata: {
  sourceType: "chat"
  chatParticipantIds: string[]  // All participants in this chat
  // ... plus each handler's existing metadata fields
}
```

These fields are added as optional properties via a `ChatSourceMixin` type, intersected with existing metadata types when applicable:

```typescript
export interface ChatSourceMixin {
  sourceType?: "chat";
  chatParticipantIds?: string[];
}
```

No complex source chain tracking. Information propagation paths can be reconstructed by correlating memory timestamps and participant overlaps across multiple chat records.
