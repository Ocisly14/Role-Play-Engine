# 单人游玩：外来者进入 Grayhaven（设计）

日期：2026-11-13 · 状态：定稿，待用户批准 · 分支基线：`grayhaven_1.3`

> 标注约定：没有标注的内容都是讨论中由用户决定的。**【实现方判断】** 是撰写者替用户做的选择，用户可以推翻。**【待定】** 是还没回答的问题。

---

## 1. 意图

把 `testmods/grayhaven` 这个现在只能"观看"的小镇模拟，做成一个**单人游戏**。玩家创建一个角色，把他扔进一直在运转的世界里。玩家可以亲自操控这个角色，也可以托管给他自己。托管时，角色碰到重要的事会像找朋友商量那样来问玩家。

这个设计的核心原则来自用户的一句话："**玩家才是主角**"。世界按真实时间流动，但凡是影响到玩家的事，世界都会停下来等玩家。

## 2. 目标 / 非目标 / 反目标

**目标**
- 玩家角色和 NPC 是同一种角色：同一份档案格式，走同一条管线（感知 → 决策 → 信任边界 → 指令收件箱 → 引擎），引擎不区分玩家和 NPC。
- 两种模式随时切换：**手动**（玩家就是角色，下的是命令）和**托管**（玩家是角色的朋友，给的是建议）。
- 世界和现实同步（一分钟一个 tick），但在需要玩家的时刻自动暂停。
- 作为**开源桌面程序**发布，玩家下载后本地运行，使用自己的模型 API key。

**非目标**
- 多人游戏，或者多个玩家共享同一个世界。
- 在线托管服务、账号体系、付费。
- 改动世界模拟本身：引擎、结算、天气、NPC 行为规则都保持不变。
- 新模组或新地图。Grayhaven 作为默认世界随程序发布。

**反目标**（技术上能跑，但只要做成这样就算失败）
- **给玩家开上帝视角**：玩家看到角色感知不到的东西，比如 NPC 的真名、没去过的地方、场景原文里此刻其实看不见的物件。
- **给玩家特权**：玩家的指令绕过信任边界或引擎判定，比如直接改世界状态，或者"我说成功就成功"。
- **托管模式下角色变成木偶**：玩家的建议被当成命令执行。角色必须保留自己的判断。
- **世界在需要玩家时没有停下**，或者玩家看不到这局已经花了多少。（托管模式下关掉窗口后世界照常运行，这是用户明确要求的，不算"空转"。见 §7 的花费上限。）
- **违反现有架构原则**：引入中央调度器、每日计划生成，或者替角色代写记忆（见 `CLAUDE.md`）。

## 3. 一局游戏的样子

1. 首次启动时，设置向导会让玩家填写模型厂商和 API key。
2. 创建角色：可以一句话快速生成，也可以手动填写，或者生成后再改。
3. 角色作为**外来者**出现在镇上的某个入口，对这个镇一无所知。
4. 玩家在主界面上读第一人称感知，下指令或者给建议。世界每分钟往前走一步，需要玩家时就停下来。
5. 关掉窗口，程序缩到托盘，世界继续运转，直到再次需要玩家时才停下，并发一条系统通知。
6. 退出游戏，世界暂停。下次启动时，从暂停的那一刻接着走。

## 4. 玩家角色：外来者

- **档案格式和 NPC 完全一样**（以 `testmods/grayhaven/grayhaven_npc/*.json` 为准）：姓名、年龄、性别、职业、外貌、性格、背景、8 项属性、状态、技能（`skillCatalog.ts` 的 17 个领域，含 Languages；没填的取目录基础值，和 NPC 一致）、语言、随身物品、长期目标（档案的 `longTermIntent` 字段，由 `seedIntents.ts` 写成记忆，和 NPC 走同一条路），以及秘密和过去的记忆（`secret` / `general` 记忆）。
- **外来者的约束**：没有 `map` 记忆，没有和镇民的关系。镇民在他眼里是 `[stranger_x]`，他在镇民眼里也是。认识谁、认识哪里，全靠游戏中角色自己写下的记忆，这正好是现有"迷路"机制的用法。
- **创建方式有三种，共用同一张表单**：
  - *快速生成*：玩家用几句话描述角色，模型按档案格式生成一份完整档案，填进表单供玩家修改。
  - *手动填写*：从空白表单开始。
  - *生成后再改*：其实就是前两种方式的组合。
  - 表单不提供 `map` 记忆和关系这两栏。
- **属性和技能的点数上限**【实现方判断】：从 Grayhaven 现有 14 个 NPC 取基准，防止填出全能角色。技能按"补上目录基础值之后"的总和计算（现有 NPC 在 328–796 之间，中位数约 370）；属性同理取中位数。快速生成的结果也要受这个上限约束。
- **入镇地点**【实现方判断】：由模组在 `module_setup.json` 里声明一个或多个"外来者入口"场景。Grayhaven 的候选是 `SCN_motel`、`ROAD_old_coast_road`、`SCN_main_north`。注意，`SCN_station_*` 是镇后那座秘密设施，不是车站，不能作为入口。入口不止一个时，玩家在创建角色时选一个。现有 `injectCharacter` 要求填 `residence`，改为使用这个入口。
- **开局时间**【实现方判断】：取玩家本地的当前钟点，日期用模组的 `startDate`（这就是"和现实同步"的字面意思）。凌晨三点开局，就会走进一个沉睡的小镇。之后每暂停一次，游戏时间就和现实时间多错开一段，这是预期中的行为。
- 现有代码 `buildInjectedProfile` 生成的档案太单薄（没有外貌，物品、关系、记忆都是空的），`injectCharacterIntoState` 还会把物品清空。需要扩展到完整档案，并把创建时填的记忆以对应类型写入记忆库。

## 5. 两种模式

### 5.1 手动模式：玩家就是角色

**玩家的每一种输入都由代码直接构造成一个 `act` 命令，不经过模型翻译。** 时长、要不要检定、难度、对抗、路线是否走得通，全部交给引擎原有的开始判定（`engine/rules/world/action-adjudication.md`）——行动者给出的时长只是参考，检定只取决于行动者是否声明了技能。所以玩家这边只需要给出引擎本来就要求行动者给的东西：做什么（文字）、涉及谁/什么（id）、用不用技能。

**一次只做一件事。** 没有队列：一件事做完、被打断，或者有事落到玩家头上时，世界暂停（见 §6），玩家再输入下一件。

四种输入：

1. **移动：点出口。** 界面只列当前地点、此刻能看到的出口（与 `perceivableDirectory` 一致，未被发现的隐藏通道不列）。点一个，代码构造"走到这个相邻地点"的命令：`objectRefs` 是目的地，`description` 用角色眼中的地名写明这一段路，所以开始判定读出的路线就是这一段。一次只走一段，想去远处就一段段点过去。门锁着、路被封了照样能点，由引擎判定走不走得通，结果写进感知。
2. **说话：说话框。** 用 `@` 选对象（可不选，即对在场的人说），写下的文字**逐字**作为 `utterance`。命令是纯说话（规则：一句话 1 分钟、不检定；说服、盘问、欺骗、威胁同样只是话，听的人信不信由他自己决定）。默认用母语；角色学过别的语言时可选用那种语言，此时 `skillId` 自动为 Languages、`language` 为所选语言。【语言选择为实现方判断】
3. **行动：行动框。** 写要做的事，用 `@` 指出涉及的人和物品，**旁边可选一个技能**（17 个能力领域之一，显示角色的技能值），也可以不选。代码构造命令：`description` = 玩家原文，其中的 `@` 引用替换成角色眼中的称呼（认识的人用名字，不认识的用感知里的描述，绝不出现 id 或真名）；`objectRefs` = `@` 到的 id；`proposedDurationTicks` 填 1（引擎会自己定）；`skillId` = 所选技能。等待也是行动框里的一件普通的事（"在这儿等一会儿"），时长由引擎判断。
4. **睡觉：一个按钮。**【实现方判断】生成一个带 `sleep: true` 的行动（触发自动存档，§7.1）。因为没有翻译器，代码无法从行动框的文字里看出"这是在睡觉"，所以单独一个按钮。

**现场对话**：普通说话在提交后立即列出玩家的原话，送达后把听清的近处听众的简短回话接在同一张卡片里，回话和玩家开口使用同一个游戏分钟。听众可以保持沉默。需要时间的后续动作仍由引擎独立开始和结算。

**`@` 列表**：此刻能感知到的人和物品，加上自己身上带的东西。来源与 `perceivableDirectory` 相同（陌生人用每个观察者固定的代号 `stranger_x`，界面显示的是角色眼中的描述，不是代号）。选中的就是 `objectRefs` 里的 id，和 NPC 从感知里抄标签是同一件事。`objectRefs` 只有 id，没有用途分类（`role` 已从引擎中删除）。

**角色做不到的事照样会失败**：失败必须以角色感知的形式出现在玩家面前，不能悄悄丢掉。被信任边界拒绝的命令（id 不存在等）直接把原因展示给玩家，不重试。

**手动模式以玩家为准，不考虑角色知不知道**：信任边界本来就不拦"角色不知道的东西"（`perceivableDirectory` 让所有真实存在的场景和非隐藏物品都可引用，引擎也不看记忆）。手动模式下玩家只能点眼前的出口、`@` 眼前的东西，所以"知道"的范围由界面自然限定。"迷路"仍是托管模式下角色自己的判断。

**记忆**：手动模式下角色的 AI 不运行，所以不会自动写记忆。玩家可以在"角色"标签页里加、改、删记忆，走和 `writeMemory` 一样的 `add/replace/delete` 语义，`map` 记忆也包括在内。陌生人的名字由玩家在关系板上填（见下）。

**关系板（类似脑图）**：
- 角色**遇到过的每个人**是板上的一个节点：代码从玩家角色的感知里记下出现过的人（与到访地图一样，不调用模型，持久化在存档里）。每个节点背后是那个人的真实 id；陌生人在界面上不显示代号和真名，名字没填时显示感知里对他的描述。
- **玩家给节点填名字 = 角色写下"我管这个人叫什么"**：复用 `writeMemory` 的同一条路径，在玩家角色对这个人的关系节点上设置 `knownAs`，节点上的备注是一条 `relationship` 记忆（"一个作者，两处索引"，手动模式下作者是玩家）。名字可以填错、可以改，那是角色自己的认知，不影响世界，对方也不会察觉。
- 填了名字之后，`@` 列表显示这个名字；这个人对角色来说就"认识"了（`isKnownTo`），渲染器在感知段落里也会用这个名字称呼他，引用他时用真实 id——和 NPC 认识一个人时的效果一样。
- **人与人之间的连线**（"Dolores —— 母子 —— Tommy"）是玩家自己的笔记：只存在关系板上，不写进角色的记忆，也不进入任何提示词或引擎。（用户确认：只是笔记）
- 托管模式下，角色自己的 AI 写下的 `knownAs` 和关系记忆同样显示在板上。

### 5.2 托管模式：玩家是朋友

- 角色由 `RoleSimAgent` 正常驱动，和 NPC 一样自己过日子。
- 遇到**它自己觉得重要**的事，会用自己的口吻来问玩家，比如"他好像是警察……要不要告诉他？你觉得呢？"。什么算重要由角色判断，不用代码规则来触发。
- 实现方式：给玩家角色的 agent 增加一个终止型工具（暂名 `askFriend`，参数是问题文本）。调用后，这一次决策就以"等朋友回话"结束。
- 玩家回话后，角色带着"朋友这样说"的上下文重新决策。玩家的话是**建议**：角色认真考虑，但最终自己决定。
- 这次对话会进入角色的感知流，角色可以按自己的判断写成记忆。【实现方判断】"玩家这个朋友"不在世界里，NPC 看不到他，也不会出现在任何场景描述中。
- 托管模式下，玩家也可以不等角色来问，**主动**在输入框里说话，性质同样是建议。【实现方判断】

### 5.3 切换模式【实现方判断】

- 随时可以切换，正在进行的行动不受影响。
- 从手动切到托管：正在等待玩家的决定作废，下一次决策交给角色自己的 AI。
- 从托管切到手动：下一次角色被叫醒时，由玩家来决定。

## 6. 时间模型：世界一直往前走，直到它需要你

- 开局时调用一次 `SimulationRunner.enableRealTimeSync()`：它会把游戏时钟**跳到**当前墙上时钟，然后按整分钟调度 tick。
- **玩家可以随时手动暂停**。暂停之后，游戏时间**从暂停那一刻接着走**，不追赶现实时间。`resume()` 本身就是这样：每个 tick 只推进一分钟，下一个 tick 等到下一个整分钟才执行。**恢复时不能再调用 `enableRealTimeSync()`**（`client/server/simulation/service.ts` 和 `mapController.ts` 现在都会调用它），否则时钟会跳回墙上时间。可以把它拆成"开局对时"和"按整分钟调度"两半，恢复时只用后一半。
- **什么时候需要玩家，沿用 NPC 被叫醒的判定依据**（`NpcActionController.processTickReport` + `decide()`）：感知到引擎判定的 occurrence、自己的行动结束（完成、失败、中断、取消）、处于空闲。成为别人检定的对象时也会叫醒，但现有 `decide()` 会跳过正在忙、又没有感知到 occurrence 的角色，所以只有在检定同时伴随一条 occurrence 时才会叫醒忙碌中的角色。沿用这个行为。不另外发明"什么算打断"的规则。
- 如果 `2026-11-13-decisions-api-fast-paths-design.md` 先落地（它让被判定为"原地不动"的角色跳过渲染和决策），**玩家角色不参与这些快速路径**，始终按上面的规则叫醒。【实现方判断】
  - **手动模式**：被叫醒时，世界暂停，把渲染好的感知推给玩家，玩家选"继续"（当前行动接着做）或输入新的行动、说话、移动（新的会替换当前行动）。
    - 自己的行动顺利完成、角色空闲时，同样暂停等玩家（没有队列可往下走）。失败、中断，或者感知到别人造成的 occurrence，都要暂停。
    - **只感知到 `trace` 的事不暂停**：occurrence 对每个感知者都有清晰度（`full` / `limited` / `trace`，定义见 `engine/rules/world/perception.md` 第 5 步）。如果这一次叫醒只是因为 `trace` 级的 occurrence，比如远处一声闷响、全镇都隐约察觉的天气或脚本事件，那么照常渲染进感知流，但不暂停，正在进行的行动照常往下走。只要有一条是 `full` 或 `limited`，就暂停。注意清晰度衡量的是"感知得清不清楚"，不是"这件事重不重要"，用户接受这一点：一件要紧但模糊的事，也只会出现在感知流里。
    - 这条 `trace` 规则只用于手动模式下是否暂停。托管模式下仍然按 NPC 的方式处理（交给角色自己的 AI 决定是否理会）。
    - 想让时间流过去，就在行动框里写"在这儿等一会儿"这类行动，时长由引擎判断。
  - **托管模式**：只有在角色调用 `askFriend` 时暂停。
- **"等玩家"必须是持久化的状态，不能靠挂起一个 Promise 来实现**【实现方判断】：这一个 tick 照常结算完，玩家角色的决策记为"待定"（手动模式下是待定指令，托管模式下是待回答的问题），runner 进入暂停，状态写进运行时存档。玩家回应后，把指令送进收件箱，或者带着回答重新决策，然后恢复运行。原因是：在等待期间退出游戏，下次启动时必须还停在这个问题上。
- 每个 tick 内的 LLM 调用如果超过一分钟，世界会慢于现实。这可以接受，不做追赶。【实现方判断】

## 7. 程序生命周期

- **关掉窗口**：缩到托盘（macOS 是菜单栏，Windows 是系统托盘），进程和世界都继续运行，直到下一次"需要玩家"时暂停。
- 暂停时如果窗口不在前台，发一条系统通知，比如"<角色名> 想听听你的意见" / "<角色名> 遇到了点事"。【实现方判断】
- **花费上限**【实现方判断】：设置里提供一个可选的"本局 token 上限"，默认关闭。达到上限时世界暂停并发通知。这是给托管模式下关窗口运行的一道保险，不改变"关窗口照常运行"的默认行为。
- **退出游戏**（托盘菜单"退出"或 Cmd+Q）：先让 runner 暂停并保存，再结束进程。下次启动时恢复到暂停那一刻。
- **一局游戏**【实现方判断】：每创建一个角色就开一局，运行时的状态保存在该局的 SQLite 文件里（见 §9），里面的内容随时都在变。启动时可以选择继续哪一局，也可以新建。

### 7.1 存档与读档

- **自动存档：角色每次睡觉时存一次。** 引擎没有"睡觉"这个状态，也没有行动类型，所以要给玩家角色加一个专用标记【实现方判断】：在玩家角色专用的 `act` 上加一个可选字段（暂名 `sleep: true`）。手动模式下由"睡觉"按钮设置（§5.1），托管模式下由角色自己的 agent 填写。NPC 的 `act` 不加这个字段，所以不影响 NPC 的提示词。开始判定接受这个行动之后，在那个 tick 结束时存档。
- **手动存档**：玩家随时可以存。如果当时正有一个 tick 在执行，就等它结算完再存。
- **存档的形式**【实现方判断】：在两个 tick 之间，把该局的 SQLite 文件复制一份快照，并带上元数据（游戏时间、场景、存档类型）。自动存档保留最近 3 个，手动存档不限数量。
- **读档**：用快照替换当前状态，世界回到快照时的游戏时间，读档后处于暂停状态。读档会丢掉当前进度，所以要先确认。
- **死亡**：玩家角色死亡时世界立即暂停（新增一个暂停原因，因为现有 `decide()` 遇到死人会直接返回，不处理的话世界会一直跑下去），然后显示死亡画面，玩家可以选择读档或者新建角色。【失去行动能力但还活着时，仍然按正常规则叫醒，由引擎判定他能做什么，这是实现方判断】

## 8. 界面

最终采用的布局（脑暴时的 v3 草图，见 `.superpowers/brainstorm/` 下的 `play-layout-v3.html`）：

```
┌──────────────────────────────────────────────────────────────┐
│ ⏸/▶  10月3日 09:14 · 小雨       [手动|托管]   本局 token 12.3k │
├────────────────────────┬─────────────────────────────────────┤
│  手绘探索地图           │  [感知] [角色]                       │
│  （底图全显；地名、路线 │                                     │
│   随到达逐个写上）      │  09:13 推门进来时门铃响了一声……       │
│                        │  09:14 靠窗的卡座里 [stranger_b]……   │
├────────────────────────┤  💬（托管时角色的问题，高亮显示）      │
│  此地 · <场景名>        │  出口：[主街] [后厨]        [睡觉]   │
│  <角色对这里的感知>     │  [说话] @… "……"   [行动] …… [技能▾] │
└────────────────────────┴─────────────────────────────────────┘
```

- **顶栏**：暂停/继续、游戏时间与天气、模式切换、本局 token 用量（因为花的是玩家自己的钱）。【实现方判断】`tokenUsage.ts` 只统计 token，没有价格表，而且是整个进程共用一个累计值。所以要改成按存档累计，并且**只显示 token 数**，不换算成美元，因为玩家可以选任意模型，价格表维护不完。
- **左上：手绘探索地图**（脑暴时的草图是 `.superpowers/brainstorm/` 下的 `handdrawn-map.html`，选的是方案 A）：
  - **底图**是一张手绘风格的模组全景插画（海岸、海湾、山坡、林子、建筑轮廓），**一开始就完整可见**，但上面**没有任何地名和路线**。插画按 `docs/art-direction/` 的美术手册制作，作为开发期的素材随程序发布，和 `client/src/observer/grayhaven/assets` 的做法一样。
  - **叠加层**是手写体的地名、路线（虚线）和步行时间，每一项都对应模组里真实的场景 id 和路段（名字取场景的 `name`，时间取路段的 `minutes`），坐标对齐到插画上。Grayhaven 可以复用 `layout.ts` 的示意坐标，以及 `grayhaven.generated.json` 导出的地点和路段。
  - **点亮规则**：角色**到达**一个地点，就用书写动画写出它的名字和到达时间。**完整走完**一段路，就画出这段路并写上步行时间，走到一半折回的不算。沿路的场所（主街上的店铺、崖间小径旁的小屋）**进去过**才以小字标在路边。只有室内、不在户外节点上的场景，归到它所在的路段或节点下。
  - 只写地名、路线和时间，不写角色的感想，那些属于记忆。
  - 点亮的依据是角色实际**到过哪里**，由代码从位置变化中记录，持久化在存档里。不调用模型，也和 `map` 记忆无关。这是用户定下的"到过什么地方就写出来"，和角色记忆里知道哪些地方是两回事：角色可以去过某处却没有写进记忆。
  - 【实现方判断】没有手绘插画和坐标的模组，退回到在空白纸面上自动排布的同一套手写叠加层。
- **左下：此地**【实现方判断】：不直接显示模组里的场景原文，那样会泄露角色此刻感知不到的东西，比如夜里看不见的物件。只显示角色**到达这里时的那段感知**，场景名作为标题。不额外调用模型。
- **右侧「感知」标签**：按时间排列的第一人称段落，里面的 `[tag]` 可以点，点击就把引用插入当前输入框；托管模式下角色的提问以高亮气泡显示。手动模式下面是 §5.1 的输入区：当前地点的出口按钮、说话框（带 `@`）、行动框（带 `@` 和技能下拉）、睡觉按钮、"继续"按钮。托管模式下只有一个给朋友的输入框。
- **右侧「角色」标签**：状态（HP / SAN / 疲劳 / 状况）、随身物品、"我记下的"（角色的记忆，可以增、改、删）、"关系板"（见 §5.1）。
- **创建角色页**：一个描述框配"生成"按钮，加一张完整的档案表单，显示点数上限的剩余量，入口场景下拉框。
- **首次启动向导**：选模型厂商，填 key，给大、中、小三档各选一个模型（有默认值）。
- 界面语言为中文（世界本来就用中文运行），沿用 `client/src/i18n`。

## 9. 技术形态

- **开源的桌面程序**【打包框架为实现方判断：Electron】：整个项目都是 TS/Node，Electron 改动最小。主进程在进程内启动现有的 Express + WebSocket 服务，监听 localhost，`BrowserWindow` 加载 Vite 构建出来的前端。要支持 macOS、Windows、Linux 三个平台。【平台范围为实现方判断】
- **数据库：SQLite**【实现方判断，用户的要求是"最简单的数据库或者不要数据库"】：一个存档就是一个 `.db` 文件，放在 Electron 的 `userData` 目录下。没有用到 pgvector，所以可以只换 provider（Prisma 6 在 SQLite 上支持 `Json` 和 enum）。需要处理的 Postgres 专属写法：`@db.Uuid`、`dbgenerated("gen_random_uuid()")`，以及 `runtimePersistence.ts` 里的 `createMany({ skipDuplicates: true })`，SQLite 不支持这个选项。`CLAUDE.md` 里"用 `db push` 而不是 `migrate dev`"的约定，到 SQLite 上需要重新审视。
- **桌面版去掉 embedding**【实现方判断】：在实际运行的路径里，embedding 只写不读。记忆是整份放进提示词的，`MemoryRetriever.query` 只能通过 `NpcMemoryManager.query/getContext` 调到，而这两个函数没有调用方。保留 embedding 就意味着设置向导要多一步模型下载，Electron 还要为三个平台打包 FastEmbed/onnxruntime 的原生二进制，却换不来任何好处。所以桌面版不写 embedding，也不打包 FastEmbed，设置向导里也没有"下载模型"这一步。
  - 备选方案：完全不用数据库，存成 JSON 文件夹。工作量更大，因为大约 40 处 Prisma 调用要重写。只有在 SQLite 的打包遇到阻碍时才考虑。
- **模型配置和 key**：桌面程序一个进程只服务一个玩家，所以现有的环境变量配置方式（`MODEL_PROVIDER`、`{SMALL,MEDIUM,LARGE}_*_MODEL`……）可以保留。设置向导把配置写进本地设置文件，启动服务前注入环境变量。key 用 Electron `safeStorage` 加密保存。【实现方判断】
- **去掉网站相关的部分**：登录、刷新令牌、邮箱验证、邀请码、一次性邮箱黑名单、访客统计、每日分析调度、按用户统计的 token 用量（对应的 Prisma 模型和 `client/server/{auth,analytics,email}` 路由）。本地单机只有一个隐含用户。【实现方判断】
- **模组**：Grayhaven 随程序发布（从 `testmods/grayhaven` 打包），沿用现有的 `moduleLoader` / `moduleImporter`。
- **NPC 范围**：沿用 `npc_injection_policy.json`，即 14 个 NPC 全部按 `daily_sim` 运行。本设计不改。

## 10. 和现有代码的接缝

| 需求 | 现有代码 | 改动 |
|---|---|---|
| 玩家角色走同一条管线 | `NpcActionController.decide()` 调用 `this.agent.decideNext(ctx)` | 对 `isPlayerInjected` 的角色，按模式分流：手动模式只记录待定决策、等玩家输入；托管模式由 `RoleSimAgent` 处理，并开放 `askFriend` 工具 |
| 玩家输入 → 命令 | `buildActionCommand`（信任边界） | 手动模式通过 `POST /simulation/:id/player/command` 提交移动、说话、行动或睡觉。`buildPlayerActArgs` 组装 `act` 参数，控制器带上玩家的引用范围和当前行动 ID，交给 `buildActionCommand`。出口与 `@` 候选取自拓扑和 `perceivableDirectory`，由 `GET /simulation/:id/player` 返回。托管建议通过 `POST /simulation/:id/player/advice` 提交。 |
| 手动模式下"跳过、继续"的语义 | `decide()` 里有"忙碌且什么也没感知到就跳过" | 保留；玩家的"继续"等价于 `continue` |
| 手动指令被拒绝时 | 命令边界返回原因 | 接口返回 HTTP 422，`/play` 显示原因。当前行动和待定决策保留。 |
| 关系板 | 关系图、`relationship` 记忆、`PlayerState` | `GET /simulation/:id/player` 返回人物、初遇时间、备注和连线。命名设置 `knownAs`，备注由玩家和 NPC 共用的 `writeRelationship` 写入。连线保存在 `PlayerState`，接口使用玩家所见的代号或人物 handle。 |
| 暂停 / 恢复 | `SimulationRunner.pause()/resume()`、`shouldPause` | 增加"因等待玩家而暂停"的原因，并持久化待定决策 |
| 现实同步 | `enableRealTimeSync()`（会把时钟跳到墙上时间） | 只在开局调用一次；恢复时只用按整分钟调度的那一半，不再对时 |
| 注入角色 | `buildInjectedProfile` / `injectCharacterIntoState` / `POST /simulation/:id/characters` | 支持完整档案、保留随身物品、写入初始记忆、改用模组声明的入口 |
| 向前端推送 | `SimulationEventEmitter` → WebSocket | `player_perceived` 推送感知，`player_pending` 包含手动决策或托管提问，`player_state` 通知状态或关系板更新。此外有 `player_map_updated`、`player_autosave_requested` 和 `player_died`。 |
| 用量 | `tokenUsage.ts`（进程级累计，只计 token） | 改为按存档累计，推送给前端；可选的上限到达时触发暂停 |
| 新的 agent 工具 | `roleSim/tools/`（`act`、`continue`、`writeMemory`） | 新增 `askFriend`，只对托管中的玩家角色开放 |

`askFriend` 需要新的提示词。要按现有规范写进 `systemPrompt.ts` 的 `*Doc` 常量里，并用 `pnpm prompt:budget` 量一下增加的 token 量。

## 11. 约束（来自 `CLAUDE.md`，实现时不得违反）

- 不引入中央调度器、不生成每日计划。手动模式下玩家一次只下一件事，引擎每次只收到一个行动。
- 信任边界照常检查玩家的指令，不给玩家开后门。
- 记忆只能由角色自己写（`writeMemory`），或者由玩家以角色本人的身份写。系统不替角色生成记忆。
- 时间统一用 `gameDateTime`。
- 不要重新引入 LangChain，不要重建 `src/planning/`。
- 不要自动提交，一次计划的改动合成一次提交。
