# 布景与道具：地点散文只写地方本身（讨论稿）

> 状态：**讨论中，未定稿**。标「已定」的是讨论里确认过的；标「提议」的是起草时补的，尚未确认。
> 关联：[2026-11-13-concealment-as-perception-design.md](2026-11-13-concealment-as-perception-design.md)（「明面上 / 没被注意到」的定义由这份设计改写，见 5.3）。

## 1. 核心想法（已定）

一个地点被呈现出来，是**某个人在某一刻**的感知：

> 呈现 = 渲染（地方本身 + 此刻的状态，经过观察者的位置、感官、认知过滤）

现在的 `description` 是作者替「默认的人、默认的时刻」做好的一次渲染，地方本身、此刻的状态、熟人才知道的事全混在里面。时间一走它就过时，陌生人会读到熟人才知道的事，物品一挪就得整段重写。

改法：地点的散文只写**地方本身**，改名为**布景**（`setting`）。此刻的状态（道具、人、光、天气、状况）各有各的来源，由渲染器在每一刻合成。散文仍然是地点的主体，因为布局、尺度、材质、各部分之间的关系拆不成字段，而且同一份布景同时交给 Engine 和渲染器，是给渲染器的想象力划边界：布景和物品行里没写的东西就不存在。

剧场的比喻和这套分层一一对应：

| 剧场 | 这里 | 来源 |
|---|---|---|
| 布景 | 尺度、布局、材质、固定件、出口、不随时间变的声音和气味 | 作者写一次：`setting` |
| 道具 | 可移动的物品 | 物品行的 `placement`，运行时会变 |
| 灯光、音效 | 光照、天气、噪声 | 代码（`sun.ts`）、天气引擎、状况 |
| 演员 | 在场的人和他们在做什么 | `charactersInScene`、`occurrences` |
| 剧本外的东西 | 历史、秘密、熟人才知道的事 | 角色记忆；必要时只给 Engine |

## 2. 现状与问题

**现在的做法**
- 每个 `SCN_*` / `ROAD_*` 有一段 `description`。它是：渲染器的场景输入、邻近地点的几何依据（`llmRenderer.ts` 约 934、1067 行）、Engine 的 Detailed Places（`contextBuilder.ts` 约 506 行）、天气引擎判断每个户外地点的依据（`weatherJudgement.ts`）、唤醒闸门的输入（`wakeGate.ts`）。
- 散文里被 `[id]` 引用的物品 = 明面上的东西（`perceivedLocation.ts` 的 `visibleItems`、`perceivableDirectory.ts`、`contextBuilder.ts` 的 `inPlainView`）。没被引用的 = 没被注意到（隐藏设计 5.1）。
- 状况（condition）也必须在散文里被引用恰好一次（`moduleSchemaV2.ts` 约 900–925 行）。
- 物品离开或进入一个地点时，Engine 必须在同一次提交里整段重写该地点的散文（`staleCitations`，`worldDeltaValidator.ts` 约 1640 行；`ITEM_OPS` 的 create / move / destroy 说明）。
- grayhaven：71 个地点文件，平均 657 字；626 个物品，只有 2 个没被引用；10 个状况。`data/Mods/grayhaven` 与 `testmods/grayhaven` 的地点文件完全一致。其余三个 `data/Mods` 模块是 v1，已经被加载器拒绝，不在范围内。

**问题**
1. **此刻的状态写死在散文里。** 蓝鸟堂座写着「满堂闲谈」「咖啡香从清早一直暖到打烊」「推开就是雾气未散的主街」，凌晨三点的空店、晴天里照样这么说。渲染器同时拿到 `charactersInScene`（实际在场的人），两份输入互相矛盾；顺着散文写，还会造出一屋子没有 tag、指不到、Engine 也不知道的人。
2. **熟人才知道的事写进了可感知层。** 「Dolores 心里都有本账」「全镇作息照它走」，物品描述里的「Earl 下午来喝咖啡就坐那儿」「Dev 来修过两回」，第一次进门的人也会读到，名字绕过了 `knownAs`。渲染器的名字守卫只拦「真名绑在 stranger 别名上」这一种情况。grayhaven 有 17 个地点文件提到 NPC 名字。
3. **挪一件道具要重写整段散文。** 为一只小费罐，模型要重写 600 多字，其他句子跟着漂移。漂移已经观察到过（`scripts/probe-description-coherence.ts` 重放的就是两次散文漂移）。
4. **状况被写成散文的一部分。** 状况是会来会走的状态（天气引擎写入、过期、被移除），引用进散文就成了「状况走了，散文还在说」。运行时新加的状况本来就不引用、单独列给渲染器，作者写的初始状况却要求引用，两套做法并存。
5. **脚本事件创建的物品对所有人隐形。** `stage-set-economy.json` 的三个补货 `item.create`（后仓存货、后厨食材、货运棚板条箱）没有、也没法让散文引用它们，按现行定义就是「没被注意到」，除非有人碰巧注意到。

## 3. 目标 / 非目标 / 反目标

**目标**
- 布景里每一句都满足：**凌晨三点、空无一人、任何天气下依然成立**（已定）。
- 道具进出地点不再需要改写布景。
- 状况、人、光、天气只从各自的来源进入呈现，布景里不写。
- 可感知层里不出现观察者不可能知道的事。

**非目标**
- 不把布局、尺度、感官拆成字段（见第 4 节方案 C）。
- 不做背景人群（已定）：热闹不热闹只看实际被模拟的人。地点在中午显得冷清，是模拟里的真话。
- 不改通道、阻挡、隐藏通道的机制。
- 不迁移 v1 模块。

**反目标**
- 布景和实况矛盾：散文说满堂，堂座里只有两个人。
- 渲染器画出布景和物品行里都没有的东西，角色对着它行动。
- 道具挪动后，旧位置的文字还在说它在那里。
- 迁移后明面上的物品变少：原来被引用的东西，迁移后被放进了容器，变成要先注意到才看得见的东西。
- 渲染器拿到了这个人没注意到的东西，靠它自己克制不写出来。

## 4. 方案对比（已定）

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 只改写作规则 | 字段不变，散文里删掉时态和熟人知识 | 便宜；但道具仍靠散文引用定义「在明面」，问题 3、4、5 都还在 |
| **B. 布景 + 道具摆放** | 散文改名 `setting`，只写地方本身；道具位置写在各自物品行的 `placement`；状况不进散文 | 解决全部五个问题；代价是 schema 升级、Engine 操作改动、71 个文件迁移 |
| C. 全结构化 | 尺度、布局、声音、气味、材质各成字段 | 这些字段没有代码会去计算，违反「字段只在代码要计算或给不同的人看时才存在」；丢掉各部分之间的关系；渲染器失去边界，自由发挥 |

选 B。

## 5. 设计

### 5.1 布景 `setting`（已定，写法细则为提议）

- `SCN_*`、`ROAD_*` 的 `description` 改名为 `setting`。车辆内部是普通场景，同样用 `setting`。
- **写什么**：尺度和形状、布局和视线、材质和磨损、墙窗门挡什么透什么、不随时间变的声音和气味（「墙皮浸透了常年的咖啡味」）、固定件、出口。
- **不写什么**：
  - 时刻、人数、天气（「满堂闲谈」「暖到打烊」「雾气未散」）；
  - 有人才会有的动静（「咖啡机嘶嘶吐着蒸汽」：要有人在操作，这是动作，由 occurrences 写）；
  - 道具（见 5.2）；
  - 状况（见 5.4）；
  - 人名，和只有熟人才知道的事（见 5.6）；
  - 氛围判断和情绪（属于观察者，交给渲染器）。
- **写法**（提议）：具体、客观、现在时。可以写得很细（「人造革裂了细纹」），不写判断，也不写此刻的状态。
- **引用**：只引用**固定件**和**出口**（出口仍按目标地点引用，规则不变）。每个都恰好一次。

### 5.2 物品的三种状态（已定）

一个放在地点里的物品，恰好处于下面一种状态：

| 状态 | 怎么表示 | 看不看得见 |
|---|---|---|
| 固定件 | 被 `setting` 引用，没有 `placement` | 看得见。地方的一部分：柜台、卡座、壁挂电话、灶台。搬走或装上它，等于地方本身变了 |
| 放在明面 | 有 `placement`，没有 `container` | 看得见。小费罐「收银机旁」，报纸「门边报纸架上」 |
| 装在容器里 | 有 `placement`，有 `container` | 每个人每一刻分别判断（见 5.3）：现金「收银机抽屉里」，蛋挞「玻璃点心柜里」 |

- **`placement` 只写位置**（已定）：一个短语，不是一段话。地点里每个不是固定件的物品都必须有，装在容器里的也一样（「收银机抽屉里」「压在床垫下」）。规范化方式与 `characterSpot` 的 `normalizeSpot` 相同：去掉方括号，长度上限 120；用名字说位置，不带 tag。
- **`container` 是装着它的那件物品的 id**（已定）：东西在另一件东西的里面、下面或后面，而那件东西有可能挡住它。抽屉、冷柜、衣柜、玻璃柜、行李箱算容器；床垫下、画框后面，床和画框也算。敞口的架子、桌面、刀座、没盖的笸箩挡不住东西，不算容器，只写 `placement`。
- **看不看得进去，由容器自己的描述说明**（已定）：透不透明、开没开、开口朝哪，都写在容器的描述里。不加任何「隐藏」标记：被挡着是容器的物理状态，对所有人都一样，和通道的 `concealed` 同一个道理。有人开关抽屉，Engine 用 `set description` 改写容器的描述。
- 「没被注意到」不再是一种状态。隐藏设计里「描述里没引用的物品 = 没被注意到」的规则，由「装在容器里、这一刻没被这个人注意到」代替。原来那 2 个没被引用的物品，迁移时找到挡住它们的物品，作为它们的 `container`。
- 加载器（提议）：同一个物品既被引用又有 `placement`，报错；地点里的物品既不被引用又没有 `placement`，报错；`container` 必须是同一地点里的物品，不能指向自己，不能成环。
- 在人身上的物品没有 `placement`，也没有 `container`。从地点到人时两者都清掉；从人到地点时由写入方给出（见 5.5）。人身上的包里装着什么，这次不处理（提议）。
- **容器被搬走，里面的东西跟着走**（提议）：一件容器换了持有者，代码把 `container` 指向它的物品（一层层往下）一起移过去，链接不变。这是结构规则，不让 Engine 逐件去写。
- 道路上的物品：`placement` 说「在哪」（「路边排水沟里」），`position` 仍然决定 5 分钟可及范围，两者并存。
- 判断固定件还是道具（提议）：**日常生活里会不会有人把它拿走**。小费罐、报纸、托盘是道具；柜台、钉在墙上的电话、收银机是固定件。拿不准的，归固定件。
- **小东西要建成物品（已定）**：会被单独拿走、使用或有意义的小东西（钱、刀、火柴、单据、药、吃的）建成自己的物品，不再只写在散文或别的物品描述里。跟着容器一起走的（小费罐里的零钱）留在容器描述里；纯背景、不太会单独拿的（架子上的盘子）留在固定件描述里，有人去动时由 Engine 建成物品（提议）。
- **容器只描述外面看得见的部分（已定）**：容器里有什么，不写在容器的描述里，而是建成装在里面的物品。否则渲染器会把容器的描述交给站在旁边的任何人，等于隔着柜门看见了里面。示例见 [2026-11-18-setting-demo/](2026-11-18-setting-demo/README.md)。

### 5.3 感知（已定）

- 明面上的物品 = 被 `setting` 引用的固定件 + 放在明面的物品。代码直接判定，所有在场的人都能指着。
- **不在明面上的东西，交给渲染器判断**（已定，2026-11-19 改）：装在容器里的物品和被挡住的通道，作为单独一组（`outOfView`）交给渲染器，每件带上自己的位置和容器的描述。渲染器结合这个人站在哪、面朝哪、在做什么、光线，判断这一刻能不能感知到；**写进段落（带标签）的，就算感知到了**，从此能指着它；没写的，就当不存在，连暗示都不许有。知道、记得、猜到东西在哪，不算感知到。
  - 原先的做法是交给 Decisions API 逐件提问（「注意到」）。实测（2026-11-19，蓝鸟三个用例）它把「知道抽屉里有钱」当成「看见了」：外来者在抽屉合着时被判注意到现金（0.76–0.96），透明柜里的蛋挞反而多数低于门槛。同一轮里，拿到现金的渲染器一次都没把它写给外来者。「注意到」这一步和它的开关 `DECISIONS_NOTICING` 一并删除。
  - 代价：渲染器拿着本不该被看到的东西，靠它自己判断，代码没有兜底；泄密可能以不带标签的模糊说法出现。需要在模拟记录里抽查。
- `unnoticedCandidates` = 这个地点里不在明面上的物品（道路上的仍受 5 分钟可及范围限制），加上被挡住的通道——就是交给渲染器判断的那一组。
- 这条规则落在 `perceivedLocation.ts` 一处：`visibleItems` 和 `unnoticedCandidates` 改用新定义。`perceivableDirectory`、Engine 上下文读同一个判断，不各自去数引用。
- 渲染器的场景块（`formatScene`）：`Setting:` 一行，然后是明面上的物品列表（带 `placement`），再是「不在明面上」的一组（带位置和容器描述）。渲染器的系统提示要写明：布景是这个地方不变的样子，此刻的人、声音、光线以输入里的实况为准；布景和物品列表里没有的东西，不要画出来。
- 邻近地点、远处地点的几何依据改读 `setting`。邻近地点块同时带上那里摆在明面的道具（名字和 `placement`），保持和现在一样：现在邻近地点的散文里本来就写着它的物品，透过开着的门能看到那边的东西（提议，我的判断）。

### 5.4 状况（已定）

- 布景里不引用状况。加载器对引用状况 id 的布景报错；状况的 `id` 仍然保留，供 `removeCondition` 使用。
- 渲染器这一侧不用改：`buildBundle.ts` 已经把全部状况（作者写的和运行时加的）作为 `activeConditions` 单独交给渲染器。现在作者写的状况在散文里和列表里各出现一次；迁移后只剩列表里那一次。

### 5.5 Engine（已定原则，操作细节为提议）

- **上下文**：Detailed Places 给出 `setting`；物品快照标明它是固定件、放在明面，还是装在容器里（带 `placement` 和 `container`）。规则照旧：Engine 知道的不等于观察者知道的。
- **`sceneChanges setDescription` 改为 `setSetting`**，只在地方本身发生物理变化时用：窗被砸了、着过火、固定件被拆走或装上。说明文字和 `scene-changes.md` 一起改写。
- **物品操作**：
  - `create` 和 `move` 加 `placement` 和可选的 `container`。目标是地点时 `placement` 必填（放下的东西总在某个位置）；藏起来就是放进某个容器（塞进抽屉、压在床垫下），写 `container`。目标是人时，两者都不许带。
  - `set` 加 `placement` 和 `container`：在同一地点里挪位置（推到柜台另一头），放进或拿出容器（`container: ""` 表示拿出来）。
  - 开关容器、把它转个方向：改写容器自己的描述（`set description`），里面的东西不用动。
  - 物品的进出、挪动不再要求 `setSetting`。
- **校验**：`staleCitations` 只对固定件生效：固定件离开或被毁，仍然要求同一次提交里有 `setSetting` 去掉它的引用。新增：提交之后，同一物品不能既被引用又有 `placement`；地点里的非固定件必须有 `placement`；`container` 必须是同一地点里的物品，不成环。
- **隐藏设计 5.5 的「私下发现」不变**：搜查成功时，结算写一条事件，发现者以 full 感知，事件引用被发现的物品，发现者由此拿到它的 tag。**「公开暴露」**改为：把东西从容器里拿出来（`container: ""`），或者打开容器（改写容器描述），之后在场的人在「注意到」那一步里看见它。不再改写散文。暗门的 `connectionConcealed` 不变。
- 规则文档 `scene-changes.md`、`item-changes.md`、`perception.md` 相应改写；`ruleTerms.ts` 里如果需要「固定件 / 道具 / 没被注意到」的定义，放在那里统一。

### 5.6 熟人知识的去向（已定原则，逐条处理为提议）

布景和物品描述里观察者不可能知道的句子，迁移时逐条处理：
- **物理现象** → 状况，或物品自身的物理描述。「吊灯会毫无征兆地闪一下」是任何人都可能看到的，留作物品描述；但「从去年冬天起」「Dolores 说是线路老了」不留。
- **某个人的习惯或知识** → 那个人的记忆，按现有规则带 tag。「Dolores 记得每个人放几块糖」进 Dolores 的记忆。
- **镇上的常识** → 镇上那些角色的记忆。
- 以上都放不下、但 Engine 裁定需要的真相：这次**不加**新字段（提议）。先迁移完，看还剩多少，再决定要不要加一个只给 Engine 的字段。

物品描述不改名，但守同一条规则：只写这件东西本身，不写人名和熟人知识。

### 5.7 脚本事件（提议）

- `item.create`、`item.move` 加 `placement` 和可选的 `container`，含义同 5.5。
- grayhaven 的三个补货事件补上 `placement`，补货才会摆在明面上（解决问题 5）。

### 5.8 天气引擎（已定）

改读 `setting`。语义反而更准：天气引擎要的正是地方本身的样子（哪里露天、哪里有遮挡），不需要此刻的状态。

### 5.9 加载器、迁移与存档（提议）

- `schemaVersion: 3`。v2 文件拒绝加载，与「v1 直接拒绝」同一做法。v3 的 `SCN_*` / `ROAD_*` 上出现 `description` 报错。
- `VEH_*` 的 `description` 是车辆外观，性质和物品描述一样，不改名。
- `testmods/DYNAMIC_WORLD_SCENE_SCHEMA.md` 按本设计重写第 2 节。
- **迁移 grayhaven 71 个地点文件**（`testmods/` 和 `data/Mods/` 两份同步），每个文件：

## 7. 风险与待定

- **画面变淡**：布景只写不变的东西，渲染出来会不会更干、更像说明书？可以拿迁移前后的同一批场景对比渲染结果。这一步要花钱调用模型，不作为验收门槛；迁移完成后由用户决定要不要跑、跑哪几个场景（提议，我的判断）。
- **Engine 藏东西时忘了写 `container`**：`placement` 必填，校验能挡住漏写位置；但「塞进抽屉」却没写 `container`，东西就成了放在明面，代码看不出来。只能靠规则文档讲清楚，再在模拟记录里抽查。
- **渲染器判断不在明面上的东西**：没有代码兜底，可能把合着的容器里的东西写出来，或用「抽屉里大概有钱」这种不带标签的说法透露。在模拟记录里抽查渲染器的输入和输出。
- **固定件和道具的边界**：收银机、挂在墙上的钟这类东西，归哪边会影响以后挪动它要不要改写布景。规则是「拿不准就归固定件」，但值得在迁移审阅时留意。
- **人名也藏在物品名、物品 id 和通道描述里**：规则要覆盖这些地方。随身物品 id 的 `item.<主人>.<东西>` 约定会把主人名字带进 tag（grayhaven 有 53 个），超出本设计，另行处理。
- **`testmods/tlou2` 本轮不处理（已定）**：它也是 v2 模块（15 个 v2 文件），`worldResolutionStageValidator.ts` 和两个 probe 脚本引用它。升到 v3 后它加载不了，引用它的地方要等它迁移或删除时一起处理。
- **物品描述和 NPC 档案是否一起迁移（待定，等用户决定）**：626 个物品描述里有 86 个提到 NPC 名字；把熟人知识挪进记忆，要改两份 `grayhaven_npc/*.json`；「镇上的常识」进哪些角色的记忆也要定。
- **626 个物品的迁移量**：脚本出草稿能减轻工作量，但审阅仍然是逐个文件。迁移验收脚本（5.9）是这一步的安全网。
