## 0. 口径说明（先读这一节，否则表会读错）

**缓存计费口径。** DeepSeek 的 `prompt_tokens` **包含**缓存命中的部分
（`hit + miss = prompt_tokens`），这和 Anthropic 相反。`tokenUsage.ts` 的
`uncachedInputTokens()`（`:292-303`）对 DEEPSEEK / OPENAI 会减掉 `cache_read`，
对 Anthropic / Google 则原样返回。本文所有表里的：

- **输入** = `prompt_tokens`（= 命中 + 未命中）
- **未命中输入** = `prompt_tokens - cache_read`，即 DeepSeek 的 `prompt_cache_miss_tokens`
- **命中率** = `cache_read / prompt_tokens`

**`cache_write` 恒为 0，这是结构性的，不是"没缓存"。** `normalizeUsageMetadata()`
（`tokenUsage.ts:146-148`）只认 `input_token_details.cache_creation` 和
`cache_creation_input_tokens` 两个 Anthropic 字段；DeepSeek 是自动缓存、
不报写入计数也不收写入溢价，所以 0 是准确的。判断缓存有没有生效只能看命中率。

**单次调用延迟没有被记录。** `ModelCallTrace`（`trace.ts:55`）的字段是
`operation / provider / modelClass / modelName / system / request / response /
usage / tools`——**没有 `durationMs`，也没有时间戳**。因此本文的耗时分两级：

| 口径 | 来源 | 精度 |
|---|---|---|
| 每 tick 墙钟 | 日志的 `[full-injection] tick N · … · 147.4s · …` 行 | **精确** |
| 三条线的阶段耗时 | trace 落盘间隔归属到各自的线，引擎段由墙钟反推 | **可验证**——tick 2–6 上三段之和与日志墙钟逐格吻合 |
| 单次调用延迟 | trace mtime 间隔 | **仅代理指标**——渲染与角色两条线并发执行，间隔会低估真实延迟 |

「阶段耗时」回答的是「这条线占用了多少墙钟」，不是「它的调用延迟加起来是多少」——
两条并发的线各自占用的时间之和仍然等于墙钟，因为每一段间隔只归属给一条线。

唯一两个**精确**的单次延迟样本是引擎的两次纠正轮（前后两条 trace 之间没有别的调用，
严格串行）：31.5 s 和 5.9 s。

**未计费的调用。** `generator.ts` 只在成功后才 `record()` + `traceModelCall()`
（`:394`/`:443`），抛异常的尝试既不进 token 账也不落 trace。日志里有 144 次
`🤖 Generating`、只有 140 条 trace——差的 4 次是被崩溃打断的在途调用，它们烧掉的
token 无从统计。本次运行没有任何重试（全部 `attempt 1/x`）。

**模型档位。** 仓库里没有任何调用点使用 SMALL 或 LARGE，也没有调用点设置
`fallbackToLargeOnFailure`，所以 `resolveModelClass()` 的 LARGE 回退分支是死代码。
本次运行中，重建全世界上下文的世界引擎和写一段景物描写的渲染器，
**跑的是同一个 `deepseek-v4-flash`**。

三条线的形状截然不同，值得先记住：

- **引擎侧**：调用次数最少（12），单次提示词最大（31–34k），命中率最高。
- **渲染侧**：调用次数最多（63），单次提示词最小（4.3–8.4k），**但独占全部输出
  token 的 67.9%**，命中率最低。
- **角色侧**：调用次数与渲染侧相当（64），输入总量最大（681k，占 43%），
  但输出最省（126k，占 10.4%）。

### 1.2 逐 tick

墙钟取自日志的 `[full-injection] tick N` 行（精确）。三个阶段耗时用的是**归属法**：
每条 trace 落盘时刻减去上一条 trace 的落盘时刻，把这段时间算在它自己那条线头上——
所有间隔加起来正好是这个 tick 的跨度。渲染与角色两条线在 tick 内交错并发执行，
所以这两列是**该线占用的墙钟**，不是「延迟之和」。

引擎段用 `墙钟 − 渲染段 − 角色段` 反推，因为直接测会跨进程调用边界（混进人工间隔
和进程启动）。**这个方法在 tick 2–6 上可以直接验证**：那五个 tick 的三段之和与
日志墙钟逐格吻合（71.3+118.4+26.8 = 216.5 对 216.4，以此类推），所以 tick 7–10

## 2. 引擎侧

### 2.1 世界行动引擎 `world-action-engine`

**调用形态。** 每个触发了裁定的 tick 开一个 agentic session
（`worldActionEngine.ts:479`，由 `tickOrchestrator.ts:263-267` 调用），
`MAX_ITERATIONS = 5`、`MAX_CORRECTION_ROUNDS = 3`，
`toolChoice: "any"` + `allowParallelCalls: true`——因为终局回合必须**同时**发出
`submit_actions` 和 `submit_effects` 两个工具调用。缓存断点有三个：系统提示一个
（`cacheSystemPrompt: true`，同时覆盖工具定义），开局用户回合的 stable 段和
volatile 段各一个（`:497-501`）。

**本次实测。**

| 2 | 1 | 30,917 | 16,837 | 14,080 | 9,291 | 45.5% |
| 3 | 1 | 31,177 | 11,337 | 19,840 | 20,710 | 63.6% |
| 4 | 1 | 31,702 | 11,862 | 19,840 | 9,873 | 62.6% |
| 5 | **2** | 99,706 | 19,066 | 80,640 | 40,616 | 80.9% |
| 6 | 1 | 31,256 | 8,344 | 22,912 | 18,320 | 73.3% |
| 7 | 1 | 32,029 | 12,189 | 19,840 | 20,758 | 61.9% |
| 8 | 1 | 32,043 | 9,643 | 22,400 | 22,704 | 69.9% |
| 9 | 1 | 32,417 | 10,017 | 22,400 | 33,433 | 69.1% |
| *10-废弃* | *2* | *106,045* | *18,109* | *87,936* | *38,748* | *82.9%* |

几个要点：

- **tick 1 没有引擎调用。** 相位 4 收集不到裁定触发就直接跳过整个 session，
  0 次模型调用——这是设计里写好的省钱路径，第一分钟没人有已提交的动作。
- **单次提示词稳定在 31–34k**，不随 tick 增长。引擎每 tick 重建全世界上下文而非
  累积历史，所以它是三条线里唯一**不会随时长膨胀**的。系统提示 61,697 字符 +
  用户回合 33,838 字符（stable 4,541 + volatile 29,297）。
- **命中率从 45.5% 一路爬到 99.7%。** stable 断点是给「下一个 tick 的同一个世界」
  读的，世界越稳定、复用越彻底。tick 10 只有 108 token 未命中——几乎整份请求都是
  缓存读。
- **`damageRoll` 一次都没被调用**，`MAX_ITERATIONS = 5` 也从未逼近：每个 session
  都在第一轮就提交完毕。唯一的多轮情形是校验驳回后的纠正轮。

**两次纠正轮**（12 次调用 = 10 个 session + 2 轮纠正，纠正率 20%）：

| trace | tick | 触发原因 | 纠正轮输入 | 其中命中 | 精确延迟 |
|---|---|---|---:|---:|---:|
| `0055`→`0056` | 5 | 两个工具都调了，但 `worldDeltaValidator` 驳回 | 67,981 | 57,728 | 31.5 s |
| `0119`→`0120` | 10（废弃） | **只调了 `submit_actions`，漏了 `submit_effects`** | 72,017 | 65,536 | 5.9 s |

纠正轮把整份请求重发一遍（输入翻倍到 68–72k），但因为 volatile 断点，
其中 85%–91% 命中缓存——这个断点正是为「本 session 的后续轮次」设的，实测生效。

`0119` 那次值得单独记：模型只发出了 `submit_actions`，违反了「终局回合必须同时
带两个提交工具」的会话契约。这是**这次运行里唯一一次模型没有遵守双工具约定**，
55 次统计里的 1 次。

**引擎调用延迟。** 同一次进程调用内的引擎段耗时：tick 2 = 71 s、3 = 172 s、
4 = 84 s、5 = 326 s（含两次调用，减去 31.5 s 的纠正轮，首轮约 294 s）、6 = 160 s。
**中位数约 160 s**——这是三条线里最慢的单次调用，输出 9k–37k token 是主因。

### 2.2 天气引擎 `weather-engine`

整场运行**只调用了 1 次**，在 tick 1，由 `module_setup.json` 的开局预设
（`OUTDOOR / snow / intensity 4`）触发的 `weather.transition` 信号引起。
之后十分钟内暴雪状态没有再变化，所以没有第二次判定。

| 输入 | 未命中 | 命中 | 输出 | 可见产出 |
|---:|---:|---:|---:|---:|
| 4,190 | 4,190 | 0 | **11,427** | 1,536 字符的 JSON |

命中 0 是必然的——这是它的第一次调用，系统提示的缓存前缀还没写入，
而它的用户回合（`weatherEngine.ts:127-132`）本来就不带 `cacheControl`，
因为每次的请求都是「这个区域这次转换」的一次性内容，不会被再读。

真正扎眼的是**输出 11,427 token 换来 1,536 字符的判定**——见第 5.1 节。

## 3. 渲染侧 `phase-g-perception-render`

**调用形态。** 每个 NPC 每 tick 一次（`npcActionController.ts:467`），
`generateText` 单轮；只有当 `uncitableTags()` 发现引用了不该引用的标签时才追问一次

```
    "Manny [stranger_3f4b46]", "Mel [stranger_6fbf22]" — scrubbing
```

这是模型把陌生人的真名和别名绑在了一起，由**确定性清洗**处理掉，没有花钱重问——
正是 `llmRenderer.ts:626-634` 记下的那个取舍在生效（那条注释记录：为这类修正
重新追问，曾在一次运行里跨十六次调用烧掉约 93k token，而清洗是免费的）。

**渲染侧吃掉了全 run 46.7% 的墙钟（2,222.5 s），是三条线里最慢的。** 单次调用从

驱动力是输出（thinking）变多，不是输入变长。

压缩阈值。

## 4. 角色侧 `role-sim-agent`

**调用形态。** 每个 NPC 每 tick 至少一次（`npcActionController.ts:340`），
命令被 intake 驳回时再来一次（`:399`，`maxRejectionRetries = 1`）。
内部是真正的 agentic 循环，`MAX_TOTAL_ITERATIONS = 14`，
`toolChoice: "any"` + `allowParallelCalls: true`。终局工具是 `act` / `continue`；
`writeMemory` 是 instant tool，设计上应当搭在终局回合里一起返回。
缓存断点：系统提示一个（约 12k 字符，模块导入时装配一次，对每个 NPC 每个 tick
逐字节相同，同时覆盖工具定义）+ 用户回合的 frozen 段一个。

**本次实测。**

## 5. 发现与风险

### 5.1 输出 token 里 87%–96% 是 thinking，不是可见内容 ⚠️ 最高优先级

`deepseek-v4-flash` 默认开启思考，**且关不掉**（`deepseek.ts:130-152` 有完整记录：
把思考关掉之后，模型在一个两分支规则上判错了，"那是拿推理预算买来的正确性"）。
后果是计费输出里绝大部分是看不见的推理：

| 线 | 计费输出 | 可见文本 + 工具参数字符 | 推理占比（保守估计） |
|---|---:|---:|---:|
| 渲染 | 822,684 | 66,740 | **≥95.5%** |
| 引擎（WAE） | 252,045 | 30,711 | ≥93.2% |
| 天气 | 11,427 | 1,536 | ≥92.5% |
| 角色 | 126,176 | 28,965 | ≥87.2% |

> 估算方法：按 1.8 字符/token 折算可见产出，这对中文是偏保守的
> （实际中文约 1.5–1.7 字符/token），所以真实推理占比只会更高。

**渲染侧是重灾区。** 63 次调用，每次产出中位数 792 字符的一段中文
（最短 191、最长 3,149），计费输出中位数却是 **13,456 token**，最高 39,179。
换算下来，一段约 470 token 的可见段落要烧掉一万三千 token 的思考。

结果就是：**渲染侧独占全run 输出 token 的 67.9%**，而它本该是三条线里最便宜的一条。
它做的事是「把结构化的感知包改写成一段第一人称散文」——一个**不需要多步推理**的
改写任务，却在为最贵的那部分买单。

天气引擎同理：一次调用 11,427 输出 token，换来 1,536 字符的 JSON 判定。

引擎侧和角色侧的推理开销是**该花的**——世界裁定和角色决策本来就是推理任务。
问题只出在渲染侧和天气引擎这两个改写/填表任务上。

### 5.2 崩溃 3 次，其中 1 次白烧了一整个 tick ⚠️

```
libc++abi: terminating due to uncaught exception of type
std::__1::system_error: mutex lock failed: Invalid argument
```

日志 175、208、313 行各一次。这是**原生层崩溃**（libc++ 抛出、进程直接 abort），
不是 JS 异常，`SimulationRunner` 的 try/catch 和 `full-injection-run.ts` 的
错误重复检测都接不住——进程死掉时 `.progress.json` 停在上一个成功的 tick，
必须人工重新 `--resume`。整场运行因此被切成 6 次进程调用。

| 崩溃 | 日志行 | 位置 | 后果 |
|---|---|---|---|
| 1 | 175 | tick 6 完成后 | 恢复点干净，无损失 |
| 2 | 208 | tick 7 完成后 | 恢复点干净，无损失 |
| 3 | **313** | **tick 10 中途** | **`0119–0127` 共 9 次调用全部作废** |

第三次的代价：**175,585 输入 token + 81,828 输出 token 白烧**，
占整场运行输入的 11.1%、输出的 6.7%。而且被打断的在途调用（144 次
`🤖 Generating` 对 140 条 trace，差 4 次）连账都没记上——`generator.ts` 只在成功后
才 record。

崩溃点的共同特征是发生在 tick 边界或 Prisma / 嵌入模型活动附近，值得往
FastEmbed（ONNX Runtime 原生线程）或 Prisma 原生引擎方向查。

### 5.3 引擎会话的双工具契约破了一次

12 次引擎调用 = 10 个 session + 2 轮纠正，**纠正率 20%**。其中 `0119` 那次是模型
只发出了 `submit_actions`、漏掉 `submit_effects`，违反了会话协议里
「每个 session 必须以一个同时携带两个提交工具的终局回合结束」的硬约定。

代价是一整轮全世界重发：72,017 输入 token（其中 65,536 命中缓存，实际未命中
6,481）。因为 volatile 缓存断点生效，纠正轮的边际成本比首轮低得多——
这个断点的设计在实测里是划算的。

另一次纠正（`0055`→`0056`）两个工具都调了，是 `worldDeltaValidator` 内容校验驳回，
属于正常的纠正机制运转，不是契约破裂。

### 5.4 两条线的提示词在线性膨胀，压缩机制未触发

| 线 | tick 1 | tick 10 | 增幅 |
|---|---:|---:|---:|
| 角色 | 8,200 | 12,911 | +57% |
| 渲染 | 4,321 | 7,506 | +74% |
| 引擎 | —（tick 2: 30,917） | 34,028 | +10% |

引擎侧几乎不涨，因为它每 tick 重建全世界上下文而非累积历史。另外两条线是
append-only 注入，会一直涨到压缩阈值。**本次 10 个 tick 内
`perceptionCompactor` 与 `memoryConsolidator` 都没有触发**——140 条 trace 里
没有 `perception-compact`、`perception-compact-tag-fix` 或 `memory-consolidate`。
这意味着这次运行**没有测到压缩路径**，长程运行的成本曲线还是未知数。

### 5.5 模拟慢了约 476 倍，渲染侧吃掉将近一半时间

10 个 tick 计算耗时 4,758.5 s，平均 476 s 模拟一分钟世界时间。前三 tick 平均
322 s，后三 tick 平均 697 s——**翻了一倍**。

墙钟按三条线归属：

| 线 | 占用墙钟 | 占比 | 调用 | 单次（tick 1 → tick 10） |
|---|---:|---:|---:|---|
| 引擎 | 1,867.9 s | **39.3%** | 13 | 中位数约 160 s |
| 渲染 | 2,222.5 s | **46.7%** | 63 | 5.5 s → **82.4 s**（15×） |
| 角色 | 668.0 s | **14.0%** | 64 | 2.7 s → 21.3 s（8×） |

**渲染侧在时间和 token 两个轴上都是最大的开销项**——46.7% 的墙钟、67.9% 的输出
token——而它的任务是三条线里最轻的（把结构化感知包改写成一段散文）。角色侧相反：
调用次数最多，只占 14.0% 的时间。

变慢的主因不是输入膨胀（提示词只涨了 57%–74%），而是**输出 token 的增长**：
全 run 输出从 tick 1 的 37k 涨到 tick 7 的 176k，而输出里 ≥92% 是 thinking
（见 5.1）。5.1 和 5.5 是同一个问题的两面。

单次调用的完成时刻间隔（**代理指标**，渲染/角色两条线并发，会低估真实延迟）：

| 线 | 样本 | 中位数 | p90 | 最大 |
|---|---:|---:|---:|---:|
| 引擎（纠正轮，**精确**） | 2 | 18.7 s | 31.5 s | 31.5 s |
| 引擎（含相位 1–4，同进程内） | 5 | 约 160 s | — | 326 s |
| 渲染 | 63 | 17.5 s | 110.1 s | 180.9 s |
| 角色 | 64 | 6.0 s | 33.6 s | 47.8 s |

## 6. 待办（本报告只记录，不实施）

1. **给 `ModelCallTrace` 加 `startedAt` / `durationMs`。** 现在完全没有单次调用
   延迟，任何延迟结论都只能靠 mtime 推。这是写这份报告时最大的阻碍。
2. **渲染侧的 thinking 开销。** 一个不需要多步推理的改写任务在为 95.5% 的推理
   token 买单，占掉全 run 输出的 2/3。注意问题不是「思考」本身，而是
   `deepseek-v4-flash` 的思考**关不掉、也不自适应**——同日的 Claude Sonnet 5 跑同一条线
   （见 `RUN_2026-09-04_anthropic_10tick_perf.md` 第 5.3 节），思考是默认开的 adaptive，
   单次输出从 334 到 2,405 token 随任务难度伸缩，中位数 497。可选方向：换一个思考量
   自适应的模型跑渲染，或者把这条线的提示词做窄到模型自己判断它不需要多想。
3. **定位 `mutex lock failed: Invalid argument`。** 3 次崩溃、1 次白烧整个 tick，
   而且原生崩溃绕过了所有 JS 层的容错。优先查 FastEmbed / ONNX Runtime 和
   Prisma 原生引擎。
4. **渲染侧缓存命中率只有 39.3%，还在回落。** 可缓存前缀太短（系统提示 12,450
   字符 + 116 字符 frozen 段）。值得看看用户回合的分段边界还能不能往后挪。
5. **补一次能触发 `perceptionCompactor` 的长程运行**，把压缩路径的成本测出来。
6. **`role-sim-agent` 的档位。** 世界引擎和渲染器共用 MEDIUM 是历史遗留；
   仓库里 SMALL / LARGE 完全没被使用，`fallbackToLargeOnFailure` 是死代码。
